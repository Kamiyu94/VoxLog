# 雲端語音辨識探索與決策紀錄（2026-06-12）

> 這是一份「決策紀錄」（ADR）。記錄我們曾經認真嘗試「用雲端 AI 做語音辨識」，
> 最後決定**移除、回歸地端**的完整理由，以及**未來什麼條件下值得重新啟用**。
> 目的：避免下次又從零踩一次同樣的坑；也讓雲端 AI 進化後，能快速判斷是否該回來。

## 背景與目標

VoxLog 原本的語音辨識（逐字稿）一律走**地端 Whisper / WhisperX**。
這次想探索：**雲端 AI（Gemini）能不能做辨識**，特別是：

- 地端在 8GB 機器（同事的 MacBook Air）上跑超過一小時的長檔容易 OOM；
- 想看雲端能否「不吃本機記憶體、又更準」。

## 做了什麼（實作摘要）

在 `transcribe_gui.py` 內實作了一條完整的雲端辨識管線：

- **Gemini File API 上傳音檔 → 原生音訊辨識**（吃音檔、吐文字）。
- **靜音感知自動切段**：用 ffmpeg `silencedetect` 找停頓，每段約 10 分鐘但切在
  最近的靜音點（不切斷句子），解決單次輸出 token 上限導致的「長逐字稿被截斷」。
- **逐段辨識再接回**：每段時間戳加偏移接回整體時間；用「具名講者＋前段結尾脈絡」
  試圖維持跨段講者一致。
- **韌性**：單段失敗自動重試（升高 temperature）、重試仍失敗就**略過該段、標記缺口、
  繼續跑完其餘段落**（不讓一段壞掉毀掉整場）。
- **FLAC 切段**降低上傳量；`http_options` 設逾時與有界重試。
- UI：辨識引擎下拉新增「雲端 Gemini」、模型只列 flash 系列、金鑰輸入/驗證、
  token 預算提示等。

## 實測發現（為什麼最後移除）

用一個真實的 56 分鐘客戶會議錄音測試，結論很明確——**對「多人會議」雲端辨識不可行**：

1. **跨段講者一致性（根本問題、無法用參數救）**
   每一段是**獨立辨識**的，Gemini 不認得與會者的聲音，只能**從音檔猜**「哪個聲音叫
   Kris、哪個叫 Kai」。每段各自猜 → 某些段猜反 → 逐字稿出現「前半把兩人標反、後半又
   換回來」。帶人名與前文脈絡只能降低機率，**沒有聲紋就無法跨段錨定**。
   → 這正是地端 WhisperX 的 pyannote 擅長的：用**聲紋向量在整檔聚類**，同一個聲音
   全程同一個 SPEAKER，使用者只要命名一次就全對。

2. **MALFORMED_RESPONSE / 重複迴圈（可重現，且付費也一樣）**
   某些段落（噪聲/靜音/交談重疊）會讓模型**陷入重複迴圈**，回傳 MALFORMED 或一路
   吐到 504 逾時。**在免費與付費金鑰上發生位置一模一樣、可重現**，證明是內容誘發、
   非帳號限速。升高 temperature 重試**只是換一次抽樣的運氣**，不是穩定解。實測 6 段
   有 2 段重試後仍失敗、只能標缺口。（旁證：切出的 FLAC 幾乎壓不掉，~19MB≈未壓縮，
   代表音訊高熵/偏吵，正是迴圈的誘因。）

3. **免費額度（RPD）與切段相乘**
   切段是「**一段算一次請求**」。免費金鑰多數 flash 模型只有 **20 次/日**，一場 1–2
   小時會議就吃掉 6–12 次，**一天只夠 1–3 場**，且可能跑到一半額度用完而中途失敗。
   只有 flash-lite 有 500/日勉強夠。免費 3.5-flash 還會被限速到逾時。

4. **成本**
   每段都把整段音檔上傳（Gemini 音訊以 **32 token/秒**計），反覆測試讓帳單明顯上升。
   地端是 $0。

## 決策

**移除雲端語音辨識，辨識一律回歸地端（Whisper / WhisperX）。**

- 多人客戶會議要「準確分辨誰說的」→ 地端 WhisperX（pyannote 聲紋）是對的工具，
  且對噪聲更耐受、又有既有的 `_collapse_repeats` 砍重複幻覺。
- 雲端 AI 仍保留在**第二步驟**做純文字的**校正 / 摘要**（Claude / Gemini / ChatGPT），
  那塊本來就好用、與本決策無關。

## 探索的副產品（已保留，讓地端更好用）

這趟雖然把雲端拔了，但順手做出的這些**都保留**：

- **辨識引擎下拉 ＋ 條件式設定列**（乾淨切換 Whisper / WhisperX）。
- **「關鍵術語 / 人名」欄 → 餵進 Whisper 的 `initial_prompt`**：地端辨識當場認對
  客戶名／人名／術語（實打實的準度提升），含 token 預算提示與自動裁切。
- **「會議背景」欄 → 餵第二步驟校正/摘要參考**。
- **模型預設依記憶體自動建議**（32GB→large-v3、8GB→small）＋記住上次選擇。
- **YouTube 改為點按鈕跳對話框輸入網址**，Cookies 收為進階選項。
- **視窗縮小、版面貼合內容、Log 變清楚**（開始/停止鈕上下排列、不再被切）。

## 未來什麼條件下值得「重新啟用雲端辨識」

下次若雲端 STT 進化到同時滿足以下幾點，就值得把這套切段管線從 git 歷史撈回來重啟：

1. **跨呼叫的聲紋級講者一致性** —— 雲端能像 pyannote 一樣，用聲音特徵在整段/跨段
   穩定對應同一個人（而不是每次重猜名字）。這是目前最大的硬傷。
2. **對含噪音檔不再陷入重複迴圈** —— 穩定 `finish_reason=STOP`，不再 MALFORMED / 504。
3. **長音檔可一次吃完、輸出不截斷**（或官方提供可靠的長音檔轉錄端點），讓切段不再必要，
   連帶解掉切段帶來的講者不一致。
4. **額度與成本合理**（不再是「一段一次請求」把每日額度與帳單吃光）。

> 被移除的完整實作（File API 上傳、靜音切段、逐段接回、具名講者脈絡、韌性重試/略過、
> FLAC 切段）可從**本紀錄對應的移除 commit 之前的 git 歷史**取回，不必重寫。
